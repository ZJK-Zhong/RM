## 2. 全车总流水线

    遥控器 / 视觉 / 上位机
                    |
                    v
    application/cmd/robot_cmd.c
                    | 产生 chassis_cmd_send、gimbal_cmd_send、shoot_cmd_send
                    v
    消息中心 PubPushMessage / SubGetMessage
                    |
       +------------+-------------+
       v                          v
    chassis.c / gimbal.c / shoot.c
                    |
                    v
    DJIMotorSetRef 或四轮 vt_*
                    |
                    v
    PIDCalculate -> DJIMotorControl 或 PowerControl
                    |
                    v
    sender_assignment[group].tx_buff -> CANTransmit -> 电调 -> 电机
                    |
                    v
    电调反馈 CAN -> CANFIFOxCallback -> DecodeDJIMotor -> motor->measure
                    |
                    +--> 下一次 PID
                    +--> 应用反馈、底盘逆解、故障判断

要分清：

- pid_ref 是“希望达到什么状态”。
- measure.speed_aps、measure.total_angle、measure.real_current 是“实际上怎样”。
- M3508/M2006 的最终输出是电调电流指令的协议值。当前 GM6020 使用 0x1ff/0x2ff 的电压控制协议；应称为最终控制量，不能把所有电机的发送值都当成安培或毫安。

## 3. 电机对象：所有数据存在哪里

打开 [dji_motor.h](E:/RM/rm-sentry/modules/motor/DJImotor/dji_motor.h:32) 第 32-66 行。

### 3.1 DJI_Motor_Measure_s

    uint16_t last_ecd;        // 上一次编码器
    uint16_t ecd;             // 当前 0-8191 编码器
    float angle_single_round; // 单圈角度
    float speed_aps;          // 度/秒
    int16_t real_current;     // 电调测得的实际电流
    uint8_t temperature;      // 温度
    float total_angle;        // 多圈角度
    int32_t total_round;      // 累计圈数

逐句理解：

1. last_ecd 用来和本次 ecd 比较，判断是否跨过 0 点。
2. ecd 是 8192 格的原始编码器读数。
3. angle_single_round 是 ecd 换算出的单圈角度。
4. speed_aps 是速度反馈，代码会把电调回传的 RPM 换成度/秒。
5. real_current 是反馈，不是 PID 输出。
6. total_round 和 total_angle 用来做多圈位置闭环。

### 3.2 DJIMotorInstance

同一文件第 49-66 行。它把一个电机需要的所有东西放在一起：

- measure：反馈抽屉；
- motor_settings：闭环、方向、反馈来源；
- motor_controller：三个 PID、pid_ref 和外部反馈指针；
- motor_can_instance：CAN 注册实例；
- sender_group、message_num：发送帧和帧内槽位；
- motor_type：GM6020、M3508、M2006；
- stop_flag：是否允许响应目标；
- daemon：反馈丢失监视器；
- dt：反馈周期。

### 3.3 设置结构体

打开 [motor_def.h](E:/RM/rm-sentry/modules/motor/motor_def.h:72) 第 72-136 行，重点看 Motor_Control_Setting_s 和 Motor_Controller_s。

| motor_reverse_flag | 目标方向是否取反 |

## 4. 反馈如何从 CAN 进入 measure

### 4.1 CAN 分发

打开 [bsp_can.c](E:/RM/rm-sentry/bsp/can/bsp_can.c:149) 第 149-169 行。

    while (HAL_CAN_GetRxFifoFillLevel(_hcan, fifox))

FIFO 里还有帧就继续处理。

    HAL_CAN_GetRxMessage(_hcan, fifox, &rxconf, can_rx_buff);

HAL 把一帧的 ID、长度和数据取到临时变量。

    for (size_t i = 0; i < idx; ++i)

遍历所有注册的 CAN 实例。

    if (_hcan == can_instance[i]->can_handle &&
        rxconf.StdId == can_instance[i]->rx_id)

同时匹配 CAN1/CAN2 和反馈 ID。

    memcpy(can_instance[i]->rx_buff, can_rx_buff, rxconf.DLC);
    can_instance[i]->can_module_callback(can_instance[i]);

先复制数据，再调用该实例的回调。DJI 电机在 [dji_motor.c](E:/RM/rm-sentry/modules/motor/DJImotor/dji_motor.c:193) 第 193-198 行把回调设为 DecodeDJIMotor。

匹配并调用回调后，第 166 行会 return，直接退出本次 CANFIFOxCallback。因此不能把前面的 while 理解成“每次一定处理完 FIFO 全部帧”，还要结合 return 的实际位置。

### 4.2 DecodeDJIMotor 逐句看

打开 [dji_motor.c](E:/RM/rm-sentry/modules/motor/DJImotor/dji_motor.c:133) 第 133-160 行。

    uint8_t *rxbuff = _instance->rx_buff;

rxbuff[0] 到 rxbuff[7] 是电调反馈的 8 字节。

    DJIMotorInstance *motor = (DJIMotorInstance *)_instance->id;

初始化时把电机对象地址放进 CAN 实例的 id 字段，这里再转换回来，找到这帧属于哪个电机。

    DJI_Motor_Measure_s *measure = &motor->measure;

保存反馈结构体地址。

    measure->last_ecd = measure->ecd;
    measure->ecd = ((uint16_t)rxbuff[0]) << 8 | rxbuff[1];

先保存旧编码器，再用高低字节拼出当前编码器。

    measure->angle_single_round =
        ECD_ANGLE_COEF_DJI * (float)measure->ecd;

头文件第 29 行的系数约等于 360/8192，把刻度变成角度。

~~~c
measure->speed_aps = (1.0f - SPEED_SMOOTH_COEF) * measure->speed_aps +
                    RPM_2_ANGLE_PER_SEC * SPEED_SMOOTH_COEF *
                    (float)((int16_t)(rxbuff[2] << 8 | rxbuff[3]));
~~~

这是第 148-149 行的完整表达式，仅为阅读重新换行：

1. rxbuff[2]<<8 把第 2 字节放到高位。
2. |rxbuff[3] 拼入第 3 字节，得到 16 位速度协议值。
3. (int16_t) 按带符号数解释；反转速度可以是负数。
4. (float) 转成浮点，参加滤波运算。
5. RPM_2_ANGLE_PER_SEC=6，所以 RPM 乘 6 变成度/秒。
6. SPEED_SMOOTH_COEF=0.85，把新样本按 85%、旧 speed_aps 按 15% 混合。
7. 左侧 speed_aps 被本次结果覆盖。右侧同名字段此时还是上一次反馈。

例如旧反馈为 0，电调报告 1000 RPM，本次滤波得到 0.15×0+0.85×6×1000=5100 度/秒；连续稳定反馈后逐步接近 6000。

~~~c
measure->real_current = (1.0f - CURRENT_SMOOTH_COEF) * measure->real_current +
                       CURRENT_SMOOTH_COEF *
                       (float)((int16_t)(rxbuff[4] << 8 | rxbuff[5]));
measure->temperature = rxbuff[6];
~~~

这是第 150-152 行：

1. 第 4、5 字节同样拼成有符号 16 位电流。
2. CURRENT_SMOOTH_COEF=0.9，所以用 90% 新样本、10% 旧值滤波。
3. 没有乘成安培或毫安的换算系数；保留电调协议量。
4. real_current 字段是 int16_t，浮点滤波结果写回时转为整数。
5. 第 6 字节直接存成温度，第 7 字节没有在这个解码器里使用。

拨弹轮应用读取的就是此处滤波后的 real_current，看到的是电调反馈，不是速度 PID 计算的输出。

    if (measure->ecd - measure->last_ecd > 4096)
        measure->total_round--;
    else if (measure->ecd - measure->last_ecd < -4096)
        measure->total_round++;

编码器从 8190 跳到 2 时，普通减法会很大，但实际只是跨过 0 点，所以用 4096 判断跨圈。

    measure->total_angle =
        measure->total_round * 360 + measure->angle_single_round;

这就是多圈反馈。

反馈写入 measure 后主要去向：

1. DJIMotorControl 或 PowerControl 下一周期读取，作为 PID 测量值。
2. chassis.c 的 OminiInverseCalculate 读取四轮速度，估算底盘实际速度。
3. 云台把 IMU 姿态和 Yaw 单圈角度发布给 CMD，用来计算底盘相对角度。发射的 Shoot_Upload_Data_s 当前是空结构体，发布 shoot_feed 尚未携带轮速、卡弹或发弹计数。底盘速度已经存入上位机发送缓存，但其 USB 运动数据发送调用目前被注释，详见第 16.3 节。

## 5. 普通电机控制：DJIMotorControl

### 5.1 取目标

### 5.2 角度环

        (uint8_t)(set >> 8);

        (uint8_t)(set & 0x00ff);

group 决定控制帧，num 决定帧内第几个电机。停止时对应两个字节清零。

第 322-329 行遍历 6 个发送组，调用 CANTransmit。

## 6. Yaw：IMU 反馈和电机反馈同时存在

打开 [gimbal.c](E:/RM/rm-sentry/application/gimbal/gimbal.c:37) 第 37-123 行。

### 6.1 身份

第 41-81 行：CAN2、ID 4、GM6020。反馈 ID 是 0x204 + 4 = 0x208。

### 6.2 反馈

第 39 行调用 INS_Init。第 65 行把角度指针指向 gimba_IMU_data->YawTotalAngle，第 68 行把速度指针指向 gimba_IMU_data->Gyro[2]。第 72-73 行把角度和速度来源都设为 OTHER_FEED。

所以当前 Yaw PID 实际使用 IMU 角度和 IMU Z 轴角速度。电机编码器仍会被 DecodeDJIMotor 写入 yaw_motor->measure，只是这两个字段不作为当前角度/速度 PID 的首选测量。

### 6.3 目标

打开 [gimbal.c](E:/RM/rm-sentry/application/gimbal/gimbal.c:130) 第 130 行的 GimbalTask，在第 155 行找到：

    DJIMotorSetRef(yaw_motor, gimbal_cmd_recv.yaw);

gimbal_cmd_recv 来自消息中心。反查 [robot_cmd.c](E:/RM/rm-sentry/application/cmd/robot_cmd.c:967) 第 967-1007 行：RobotCMDTask 根据遥控器、视觉或上位机产生 gimbal_cmd_send，并发布 gimbal_cmd。

### 6.4 完整旅程

1. 输入产生 yaw 目标。
2. robot_cmd.c 写入并发布 gimbal_cmd_send.yaw。
3. GimbalTask 收到 gimbal_cmd_recv.yaw。
4. DJIMotorSetRef 只把目标写进 motor_controller->pid_ref。
5. DJIMotorControl 用 IMU 角度和速度跑 PID。
6. 最终控制量写进 CAN2 的 0x1ff 帧、tx_buff[6] 和 tx_buff[7]。
7. CAN2 控制帧到 GM6020。
8. 电调回传 0x208，DecodeDJIMotor 写回 yaw_motor->measure。

### 6.5 调试变量

看 gimbal_cmd_recv.yaw、gimba_IMU_data->YawTotalAngle、gimba_IMU_data->Gyro[2]、yaw_motor->motor_controller.pid_ref、yaw_motor->measure.ecd/speed_aps/real_current、yaw_motor->stop_flag。

目标变但 pid_ref 不变，查订阅；pid_ref 变但 IMU 不变，查 INS_Task；反馈正常但不动，查发送组、方向和供电。

| current_control_mode | CMD 内部 | 决定本周期执行哪个整车模式函数 | MOVE、SPIN、FIRE |

另外，SHOOT_ON、FRICTION_ON、LOAD_BURSTFIRE 是发射机构自己的三个开关，后面第 9 章会分别分析。

因此即使右摇杆不动，底盘仍会旋转去跟随云台。反过来，offset_angle=-20 度时四轮目标均为 -600。

| 电机 | 轮速表达式 | 目标 |
|---|---|---:|
| LF，ID 2 | vx-vy+vw | +494.97 |

### 8.12 所有模式共用的坐标变换，逐句分析

打开 [chassis.c](E:/RM/rm-sentry/application/chassis/chassis.c:329) 第 329-348 行。

### 8.14 四轮目标怎么进入 PID，而不是直接变成电流

打开 [chassis.c](E:/RM/rm-sentry/application/chassis/chassis.c:256) 第 256-267 行：

~~~c

~~~

第 263 行把左前目标写进 motor_lf->motor_controller.pid_ref；第 264 行写右前；第 265 行写左后；第 266 行写右后。

打开 [power_control.c](E:/RM/rm-sentry/modules/motor/power_control.c:294) 第 294-318 行：

~~~c

~~~

它用电机转子的 RPM 做测量。因此数值目标最后是按电机 RPM 参与闭环。当前 OminiCalculate 没有使用轮周长和减速比把线速度换算成 RPM，摇杆系数和导航系数是实际使用的比例，几何单位并没有完整贯通。

手算一个左前电机：速度目标 600，电机反馈 speed_aps=2400 度/秒。

~~~text
反馈 RPM=2400/6=400
速度误差=600-400=200
Kp=10，Ki=Kd=0
PID 原始输出=10×200=2000
~~~

2000 是电流指令协议值，不是目标 600，也不是反馈 400。如果总功率超限，它还会经过功率控制再次变化。

底盘速度反馈使用的是减速前电机转子 RPM；若要解释真实车速，还需除以轮减速比并使用轮子半径。

### 9.2 SHOOT_OFF：摩擦轮主动减速，拨弹轮清零输出

## 10. 拨弹轮如何一颗一颗送弹，程序如何保证单发

先回答你最关心的问题：机械的分弹结构能把连续运动分成一颗一颗的送料动作；要让一次命令准确对应一颗，还需要电控记录一次触发、计算每发角度、闭环走到目标并确认完成。当前代码实现的是连续速度送料，后面这些精确单发步骤尚未形成有效执行链。

下面分别把机械、单位、注释代码和完整控制过程讲清楚。

### 10.1 三个发射电机各自做哪件事

典型拨盘式机构的过程是：

~~~text
弹舱中的弹丸
 -> 拨盘槽位或拨齿按机械间距取弹
 -> 经过固定送弹口进入导弹管 / 发射入口
 -> 进入左右摩擦轮之间
 -> 两轮接触面共同朝出弹方向运动，给弹丸加速
 -> 弹丸离开发射口
~~~

拨弹轮负责把弹丸依次送到入口；摩擦轮主要负责加速。具体槽数、导弹管布局和是否有额外分弹机构要对照你这辆车的机械，源码不能证明每个槽每次都装到一颗。

连续拨盘转过一个槽距就经过一次送弹位置，因此可以观察到弹丸逐颗进入。但电机编码器只告诉程序转了多少，不告诉程序“这个槽里一定有弹”。

### 10.2 从头文件找出每颗弹对应多少角度

打开 [robot_def.h](E:/RM/rm-sentry/application/robot_def.h:35) 第 35-37 行：

~~~c
#define ONE_BULLET_DELTA_ANGLE 36
#define REDUCTION_RATIO_LOADER 36.0f
#define NUM_PER_CIRCLE 10
~~~

| 行 | 逐句解释 |
|---:|---|
| 35 | 宏替换：ONE_BULLET_DELTA_ANGLE 在使用处被替换成数值 36 |
| 36 | 定义拨弹传动减速比 36:1 |
| 37 | 配置拨盘一圈对应 10 个装载位置 |

这些是工程配置，实车是否为 10 槽还要核对机械。

若拨盘一圈有 N=10 个等距有效送料位置：

~~~text
拨盘输出轴一圈 = 360°
每颗弹的输出轴步距 = 360° / 10 = 36°
~~~

36 度是拨盘输出轴的步距。另一个“36”是减速比，它们恰好数值相同，但含义不同。

### 10.3 最容易弄错的一步：拨盘角度和电机转子角度

按常见 M2006 减速前转子编码器反馈，电机转子每转 36 圈，拨盘输出轴才转 1 圈。额外机械传动若存在，应把它计入总减速比。

本工程 [dji_motor.c](E:/RM/rm-sentry/modules/motor/DJImotor/dji_motor.c:146) 第 146-159 行只做编码器到角度的转换，没有除 REDUCTION_RATIO_LOADER：

~~~c
measure->angle_single_round = ECD_ANGLE_COEF_DJI * (float)measure->ecd;
measure->total_angle = measure->total_round * 360 + measure->angle_single_round;
~~~

因此用于角度环的 total_angle 保持的是编码器轴累计角度。按上述转子反馈，准确走一槽需要：

~~~text
输出轴每发步距 = 360 / N
转子每发步距 = (360 / N) × R
N=10，R=36
转子每发步距 = 36 × 36 = 1296°
                  = 电机转子 3.6 圈
~~~

例如测得当前 total_angle=7200 度，送料正方向取正：

~~~text
单发目标 = 7200 + 1296 = 8496°
三发目标 = 7200 + 3×1296 = 11088°
~~~

若方向设计相反，则减去对应步距。当前 loader 配的是 NORMAL，不能把别的车的方向直接搬过来。

### 10.4 编码器 0-8191 怎么测出超过一圈的角度

打开 [dji_motor.c](E:/RM/rm-sentry/modules/motor/DJImotor/dji_motor.c:145) 第 145-159 行。

假设上一帧 ecd=8000，本帧 ecd=200：

~~~text
ecd-last_ecd = 200-8000 = -7800
-7800 < -4096，因此 total_round++
angle_single_round ≈ 200×360/8192 = 8.79°
total_angle = total_round×360 + 8.79°
~~~

编码器回到 0 附近时，多圈累计角度不会直接掉回 0，才能追踪转子连续转过 1296 度。

跨圈算法要求两次采样间转过小于半圈，且上电第一个编码器样本可能产生基准偏移；相对送料目标应基于已稳定收到的反馈，不假设上电 total_angle 必然是机械零点。

按 8192 刻度/转子圈计算，1296 度约对应 29491.2 个累计刻度。这是跨多圈的累计量，不可能用一个 0-8191 的单圈 ecd 直接表达。

### 10.5 当前连续速度如何形成射频

当前 [shoot.c](E:/RM/rm-sentry/application/shoot/shoot.c:187) 给 +10000 度/秒。

按上述 N=10、R=36 的机械假设，无卡弹、无空槽且转速稳定时：

~~~text
转子速度 = 10000 度/秒
转子 RPM = 10000/6 ≈ 1666.67 RPM
拨盘输出轴速度 = 10000/36 ≈ 277.78 度/秒
每颗输出轴步距 = 36 度
理论射频 = 277.78/36 ≈ 7.72 发/秒
理论每发间隔 ≈ 1/7.72 ≈ 0.1296 秒
~~~

也可以直接用转子每发角度计算：

~~~text
理论射频 f = 转子速度 / 转子每发步距
           = 10000 / 1296
           ≈ 7.72 发/秒
~~~

这里是送料位置经过入口的理论频率，不是程序实际计数得到的枪口发弹频率。空槽、打滑、反转和堵转都会改变真实结果。

如果想从期望射频推回速度，公式是：

~~~text
转子速度目标 = f × 360 × R / N
~~~

例如 5 发/秒、N=10、R=36 时，需要 6480 度/秒；10 发/秒对应 12960 度/秒。

当前 shoot_rate 字段没有参与有效连发计算，修改它不会改变这个写死的 +10000 目标。

### 10.6 为什么“连发时逐颗出弹”不等于“一个命令只打一颗”

当前 FIRE 模式保持期间，机器人任务约每 5 ms 再次写入同样的 +10000 速度目标。电机任务约每 1 ms 继续执行速度 PID。它没有在走过一个槽距后把目标停止。

在理想稳定速度下，持续 0.5 秒的 +10000 目标会经过约：

~~~text
0.5 × 7.72 ≈ 3.86 个送料间距
~~~

不能由此保证刚好送 4 颗，因为启停加减速、槽位初始相位和弹丸是否装满都影响结果。

“给速度，再延时一段时间”只能估计送料量；位置单发应给一次固定的相对角度目标，并等待到位。

### 10.10 一个完整的准确单发应该怎样走

| 7500 | 8796 | 1296 |
| 8000 | 9296 | 1296 |

目标不断向前移动，电机永远看见相同的正误差，就无法在“一发位置”停下来。

正确思路是新事件时生成一次目标，运动中只重复使用同一个目标值。

### 10.12 防重复触发：电平、边沿和不应期

当前 fire 是电平控制：只要为真，每周期都维持 LOAD_BURSTFIRE。这适合连续发射。

准确单发需要区分“这次刚按下”和“仍在按住”。一种教学写法是上升沿检测：

~~~c
/* 教学伪代码，不在当前工程中 */
new_event = fire_now && !fire_last;
fire_last = fire_now;
~~~

第一句只有从 0 到 1 的周期为真；第二句保存本次状态供下一周期比较。先判断、后保存，顺序不能反。

例如 fire 连续为 0、1、1、1、0，只有第一个 1 产生事件。上位机也可以发送事件编号，用编号区分新请求；这是另一种通信设计。

原注释中的 150 ms 不应期只能暂时抑制重复进入。若一直保持 LOAD_1_BULLET，时间到后仍会再次进入，所以它本身不能保证“整次按住只打一颗”。

下面是展示单发状态关系的图：

~~~text
等待新事件
  -> 许可条件满足，计算固定位置目标
  -> 送料中，持续检查编码器和速度
  -> 到位且低速稳定
  -> 记录完成
  -> 等待下一个事件

送料中若超时 / 电流持续异常 / 角度不前进
  -> 卡弹处理或停止
  -> 明确这一次动作失败、重试还是取消
~~~

没有新事件时，等待状态不能继续累加一发角度。

### 10.13 位置到位为什么仍不能证明子弹出去了

编码器证明的是传动轴运动。空槽时轴也可以正常走到目标；传动松脱时转子也可能转完，但拨盘没有正确运动；弹丸在后段堵住也可能不立刻反映为同样的角度误差。

因此应该区分：

| 观察量 | 能证明什么 | 不能单独证明什么 |
|---|---|---|
| total_angle 到位 | 编码器轴到目标 | 一颗弹丸已经离开枪口 |
| 电流突变 | 负载变化 | 变化一定来自真实发弹 |
| 机械槽距 | 送料位置的间隔 | 每槽一定有弹 |
| 裁判系统发射反馈 / 专用弹丸传感器 | 可用于确认实际发弹事件 | 当前空的 shoot_feed 已经上传了这个信息 |

当前代码没有把这类确认量闭合成单发计数状态机。讲“准确送一颗”时，既要看电机定位，也要看机械分弹和实际发弹确认。

## 11. PIDCalculate：把目标和反馈逐句变成输出

打开 [controller.c](E:/RM/rm-sentry/modules/algorithm/controller.c:159) 第 159-221 行。

函数有三个参数：

~~~c
float PIDCalculate(PIDInstance *pid, float measure, float ref)
~~~

pid 是这个电机正在使用的 PID 对象地址；measure 是测量值；ref 是目标；返回值是浮点控制输出。

### 11.1 当前真正执行的计算语句

~~~c
pid->Measure = measure;
pid->Ref = ref;
pid->Err = pid->Ref - pid->Measure;
pid->Pout = pid->Kp * pid->Err;
pid->ITerm = pid->Ki * pid->Err * pid->dt;
pid->Dout = pid->Kd * (pid->Err - pid->Last_Err);
~~~

| 行 | 一句一句看 |
|---:|---|
| 168 | 将这次测量保存在 PID 对象，调试器可以直接观察 Measure |
| 169 | 保存这次目标 Ref |
| 170 | 相减得到误差 Err；目标大于实际时误差为正 |
| 176 | 比例项 Pout=Kp×当前误差 |
| 177 | 本次积分增量 ITerm=Ki×误差×dt；还不是累计积分 Iout |
| 179 | 当前微分项使用两次误差之差；没有除 dt |

再看：

~~~c
if (pid->Improve & PID_Integral_Limit)
    f_Integral_Limit(pid);
pid->Iout += pid->ITerm;
pid->Output = pid->Pout + pid->Iout + pid->Dout;
f_Output_Limit(pid);
pid->Last_Err = pid->Err;
return pid->Output;
~~~

| 行 | 一句一句看 |
|---:|---|
| 195-196 | 用按位与判断积分限幅标志，启用时先限制积分累积 |
| 198 | 把本周期积分增量累加到 Iout |
| 199 | 把 P、I、D 三项相加 |
| 206 | 限制总输出在 ±MaxOut |
| 215-219 | 保存测量、输出、误差等供下一周期使用 |
| 221 | 把输出返回给电机控制函数 |

### 11.2 配置参数不等于这项功能正在执行

第 165 行的 dt 更新被注释。PIDInit 第 145 行清零 PID 对象，第 149 行初始化时间计数器，却没有给 pid->dt 赋非零采样时间。

按当前初始化和执行路径，dt 保持为 0，所以即使 Ki 写成非零，ITerm=Ki×Err×0 仍为 0。不能看到云台 Ki=45 就宣称积分已经在累积。

第 182-193 行的梯形积分、变速积分、微分先行和微分滤波调用均被注释；第 201-203 行的输出滤波调用也被注释。配置 Improve 中有对应标志，并不会让一段注释代码自动执行。

当前底盘与摩擦轮的 Ki、Kd 本来为 0，所以数值手算主要按 P 项即可。若以后分析云台调参，要以这些实际语句为准。

### 11.3 底盘、发射、Yaw、Pitch 分别经过哪些环

| 电机 | 当前入口目标 | 第一层 | 第二层 | 当前最终打包 |
|---|---|---|---|---|
| 四个底盘轮 | 电机 RPM 数值目标 | 速度 PID | 四轮功率控制 | C620 电流指令协议值 |
| 左右摩擦轮 | 度/秒 | 速度 PID | 无当前有效电流环 | C620 电流指令协议值 |
| 拨弹轮 | 度/秒 | 速度 PID | 无当前有效角度环或电流环 | C610 电流指令协议值 |
| Yaw | IMU 角度目标 | 角度 PID | IMU 速度 PID | GM6020 控制协议值 |
| Pitch | IMU 角度目标 | 角度 PID | 当前没有速度 PID | GM6020 控制协议值 |

“配置里有 current_PID”与“执行了 current_PID”也是两回事。摩擦轮和拨弹轮的 close_loop_type 只有 SPEED_LOOP，所以电流 PID 参数块当前不会进入控制链。

### 11.4 一个拨弹轮的真实速度闭环例子

假设速度参考为 +10000，反馈 speed_aps=9000：

~~~text
Err = 10000-9000 = 1000 度/秒
Kp=2.8，Ki=Kd=0
Output = 2.8×1000 = 2800
~~~

如果电流条件触发，应用层下个周期把目标改成 -10000，而电机反馈仍暂时为 +9000：

~~~text
Err = -10000-9000 = -19000
Pout = 2.8×(-19000) = -53200
MaxOut=20000，因此 PID 返回 -20000
~~~

这表现为较大的反向输出，电机不会瞬间从正速度跳成负速度。反馈跟不上目标是一个物理过程，控制任务继续周期计算。

这个例子计算的是 PID 阶段，电调允许的指令范围仍要按 C610 协议核对；当前底层直接将返回值转成 int16_t 并打包。

## 14. 最后记住十句话

1. pid_ref 是目标，最终 CAN 控制量要经过 PID 和相应限制才能得到。
2. 反馈先经过 CANFIFOxCallback，再由 DecodeDJIMotor 写入 measure。
3. measure 是电机实际状态的统一入口。
4. 云台和发射通常由 DJIMotorControl 控制。
5. 底盘由 PowerControl 控制，因为四轮共享功率上限。
6. DJIMotorSetRef 只存目标，不会立刻发 CAN。
7. 启用串级时角度环输出进入速度环；当前 Pitch 只有角度环，输出直接打包。
8. Yaw/Pitch 可以使用 IMU，Yaw 编码器仍被用于底盘相对角度。
9. 底盘先运动学分解，再速度 PID 和功率缩放。
10. 查任何电机都按：身份 -> 目标 -> 反馈 -> PID -> 发送组 -> CAN -> 回流。

## 17. 底盘功率控制逐句读：为什么目标对了，输出仍可能变小

打开 [power_control.c](E:/RM/rm-sentry/modules/motor/power_control.c:227)，先看第 227-282 行，再看第 287-415 行。

### 17.1 谁给底盘的最大功率

ChassisTask 在 [chassis.c:293](E:/RM/rm-sentry/application/chassis/chassis.c:293) 调用：

~~~c
SetPowerLimit(referee_data->GameRobotState.chassis_power_limit);
~~~

SetPowerLimit 在 power_control.c 第 58-60 行把传入值写入 chassis_max_power。

但 PowerControl 第 255-281 行在超级电容实例存在时还会重新赋值：

~~~c
SuperCap_Feedback_t cap_feedback = SuperCapGet(super_cap_pr);
if (cap_feedback.chassis_power_limit_w > 0) {
    chassis_max_power = cap_feedback.chassis_power_limit_w * 0.95f;
} else {
    chassis_max_power = 45.0f;
}
~~~

第 273 行读取超电反馈；第 276 行检查反馈可用功率为正；第 277 行使用其 95%；否则第 280 行使用 45 W。

因此要看运行时最后写进 chassis_max_power 的值，不能只看裁判系统那一个输入。第 266-267 行发送给超电的裁判功率/缓冲当前写死为 100 和 57，这同样属于实际生效的数据来源。

### 17.2 每个电机先算速度 PID，再估计功率

第 290-318 行的关键语句：

~~~c
motor = dji_motor_instance[i];
motor_controller = &motor->motor_controller;
measure = &motor->measure;
pid_ref = motor_controller->pid_ref;
pid_measure = measure->speed_aps / 6.0f;
pid_ref = PIDCalculate(&motor_controller->speed_PID, pid_measure, pid_ref);
initial_torque[i] = pid_ref;
power_control_out[i] = pid_ref;
A = a * initial_torque[i] * initial_torque[i];
B = k2 * pid_measure * pid_measure;
C = toque_coefficient * pid_measure * initial_torque[i];
initial_give_power[i] = A + B + C + constant;
~~~

| 行 | 逐句分析 |
|---:|---|
| 290 | 本文件数组中的第 i 个底盘电机；注册顺序 i=0/1/2/3 对应 LF/RF/LB/RB |
| 292-293 | 取控制器和测量结构体地址 |
| 294 | 保存该电机目标 |
| 310 | 转子速度从度/秒换成 RPM |
| 312 | 速度 PID 输出赋回局部 pid_ref，此时它已不再是速度目标 |
| 313 | 保存原始 PID 输出；变量虽叫 initial_torque，这里没有先换成 N·m |
| 314 | 预设最终输出为这个原始值 |
| 315 | 根据输出平方计算一项损耗模型 |
| 316 | 根据转速平方计算另一项 |
| 317 | 用转速和控制量的乘积估计机械功率相关项 |
| 318 | 相加再加固定损耗，得到估计功率 |

所以 initial_give_power[i] 是估计功率，power_control_out[i] 才是后面打包的控制量。名字相近，单位完全不同。

第 239-244 行模型参数为 a=1.23e-7、k2=1.453e-7、toque_coefficient≈1.99688994e-6、constant=4.081。

以某轮 RPM=400、PID 输出=2000 为例：

~~~text
A = 1.23e-7 × 2000² = 0.492
B = 1.453e-7 × 400² ≈ 0.02325
C = 1.99688994e-6 × 400 × 2000 ≈ 1.59751
估计功率 ≈ 0.492+0.02325+1.59751+4.081 = 6.19376 W
~~~

这是当前模型的数值演示；模型是否准确要通过台架数据确认。

### 17.3 四轮合计超过上限时发生什么

第 327-334 行累加非负的 initial_give_power；负值按模型视为发电，不参与这次正向功率合计。

第 340-349 行：

~~~c
if (initial_total_power > chassis_max_power)
{
    float power_scale = chassis_max_power / initial_total_power;
    /* 后面的循环逐轮处理 */
    scaled_give_power[i] = initial_give_power[i] * power_scale;
}
~~~

这里摘出核心比较和缩放赋值，完整循环在原函数中。

如果四轮估计各 25 W，总计 100 W，而上限为 80 W：

~~~text
power_scale=80/100=0.8
每轮分配功率=25×0.8=20 W
~~~

注意乘 0.8 的是功率，不是直接把电流指令乘 0.8。

### 17.4 从分配功率反求控制量

第 352-373 行把电机实际 RPM 代入二次模型，计算：

~~~c
float b_coef = toque_coefficient * speed_rpm;
float c_coef = k1 * speed_rpm * speed_rpm - scaled_give_power[i] + constant;
float delta = b_coef * b_coef - 4.0f * a * c_coef;
~~~

它要解 a×I²+b×I+c=0，I 是此处的控制量。delta 是判别式；第 361-362 行把负判别式置为 0；第 365 行按原输出符号选择根；第 368 或 373 行把结果限制在 ±16000。

有一个具体的不一致：正向估计第 316 行用 k2，逆解第 357 行仍用 k1。第 356 行注释说应改成 k2，但语句没有改。你现在阅读时必须按实际 k1 计算，不能照注释把它当作已修正。

### 17.5 最终打包与 STOP 覆盖

第 387 行把 power_control_out[i] 转成 int16_t；第 398-401 行按电机 group/num 写高低字节；第 404-405 行 STOP 时清零；第 413 行提交 CAN 帧。

运动目标、PID 输出、功率分配、最终打包是四个阶段。排查“底盘目标很大却转不快”时，要逐级比较这些变量。

## 18. 跟着观察整辆车：先预测，再对照反馈

这一章是阅读和调试变量练习。理解源码时可以先只纸上计算；实际观察电机运动时先用无弹、低速、机械允许的方式建立方向对应。

### 18.1 两个任务和一个 CAN 接收路径

打开 [robot.c](E:/RM/rm-sentry/application/robot.c:58) 和 [robot_task.h](E:/RM/rm-sentry/application/robot_task.h:112)。

~~~text
机器人任务：约 5 ms 延时
  RobotCMDTask -> GimbalTask -> ShootTask -> ChassisTask

电机任务：约 1 ms 延时
  DJIMotorControl -> PowerControl

CAN 接收中断：
  收到一帧 -> CANFIFOxCallback -> 对应 DecodeDJIMotor -> 更新 measure
~~~

5 ms 和 1 ms 是任务里的 osDelay 参数，实际周期还包含执行时间和调度；不能当作精确固定时钟。

应用写一次目标，电机任务可以在两次应用更新之间多次用最新反馈计算输出。CAN 接收也不需要等 RobotTask 才更新反馈。

打开 [motor_task.c](E:/RM/rm-sentry/modules/motor/motor_task.c:14) 第 14-15 行，可直接看到普通电机控制和底盘控制依次被调用。

### 18.4 学习题 A：MOVE 变 SPIN

已知无平移、offset_angle=20 度：

1. MOVE 的 wz 是多少？
2. MOVE 四轮目标是什么？
3. 切 SPIN 后 wz 是多少？

答案：MOVE 的 wz=3，四轮目标各 600；SPIN 的 wz=14，四轮目标各 2800。两种模式 SHOOT_OFF，摩擦轮使能给零速度，拨弹轮 STOP。

### 18.5 学习题 B：摩擦轮模式变 FIRE

已知同一组右摇杆输入，云台相对角不变：

1. 四个底盘目标公式会变化吗？
2. 哪个发射字段变化？
3. 两个摩擦轮对象为何都存正目标，而反馈预计符号相反？
4. loader 的 total_angle 经过一槽后会自动停止吗？

答案：四轮仍是 mode=2、NO_FOLLOW；load_mode 从 STOP 变 BURST。左摩擦轮底层有 REVERSE。当前 loader 是速度连发，不会在一槽后自动停止。

### 18.6 学习题 C：一次精确单发的单位

假设 N=10、总 R=36，total_angle=7200 度：

1. 输出轴一发步距？
2. 转子一发步距？
3. 单发位置目标？
4. 如果只给 total_angle+36，输出轴转多少？
5. 为什么不能每周期重新算当前角度+1296？

答案：36 度、1296 度、8496 度；只加 36 对应输出轴 1 度。每周期重算会让目标不停前移，电机无法完成这个固定的一发位置任务。

### 18.7 学习题 D：位置到位和实际发弹

如果 total_angle 已到目标，但拨盘这个槽里没有弹，能否把它记为一次已确认发弹？

不能。位置反馈只能确认编码器轴运动完成，实际发弹需要对应机械事实或发弹检测反馈。当前工程未实现这条确认和计数链。

### 18.8 遇到不懂的某一句，按四个问题拆开

例如：

~~~c
DJIMotorSetRef(motor_lf, vt_lf);
~~~

1. 谁写这句？ChassisTask 调用的 LimitChassisOutput。
2. 参数是什么？左前电机对象地址和解算后的左前目标。
3. 改了哪里？motor_lf->motor_controller.pid_ref。
4. 谁下一步用？PowerControl 读取目标，配合电机速度反馈算输出。

再例如：

~~~c
DJIMotorSetRef(loader, loader->measure.total_angle + ONE_BULLET_DELTA_ANGLE);
~~~

1. 这句现在执行吗？不执行，在单发注释方案里。
2. 它本意设什么？相对位置目标。
3. 两个角度的坐标一致吗？当前编码器角度未除减速比，宏 36 按槽距解释时不一致。
4. 只靠这句能完成单发吗？还缺有效角度闭环配置、一次事件、固定目标、到位判定等。

能够把这四问回答出来，比仅记住函数中文含义更接近独立读懂整车控制代码。
